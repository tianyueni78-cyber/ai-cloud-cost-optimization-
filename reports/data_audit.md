### 2.2 使用记录的业务重复

按“标准化资源池 ID + UTC 小时”检查时，样例中同时出现：

- 两行共用同一 `usage_record_id`；
- 两行具有不同 `usage_record_id`。

第二轮完整统计结果：

| 指标 | 数量 |
|---|---:|
| 重复业务键 | 259 |
| 额外行 | 259 |
| 同一记录 ID 的重复组 | 139 |
| 不同记录 ID 的重复组 | 120 |

这说明需要区分主键重复与业务重复。下一轮仍需比较相同记录 ID 的重复行是否所有指标完全一致，并为不同记录 ID 的业务重复定义保留规则。

### 2.3 必填标识

- 资源清单的关键字段在当前可见输出中未发现空值。
- 使用表的 `usage_record_id` 未发现空值。
- 账单的 `billing_line_id` 和 `net_cost_usd` 未发现空值。
- SLA 的 `team_id` 和 `product_id` 未发现空值。
- 业务事件中各有 1 行缺少 `team_id` 和 `product_id`。事件字段允许为空，需结合事件类型判断是否属于公司级或区域级事件，不能直接标记为错误。

第二轮补全了使用表和账单的主要空值统计：

| 表 | 字段 | 空值行数 |
|---|---|---:|
| 使用 | `active_gpu_count` | 0 |
| 使用 | `gpu_utilization_pct` | 630 |
| 使用 | `memory_utilization_pct` | 398 |

| 使用 | `queue_time_seconds` | 235,193 |
| 使用 | `availability_pct` | 239 |

| 账单 | `contract_id` | 420 |
| 账单 | `billed_gpu_hours` | 129 |
| 账单 | `unit_rate_usd` | 129 |

`p95_latency_ms`、`queue_time_seconds`、合同和计费用量允许在部分业务类型中为空。以上数字是待分类空值，不能直接等同于数据缺失问题。

第三轮按业务类型拆分后确认：

- `Batch` 和 `Training` 的 `p95_latency_ms` 全部为空，符合非在线负载不记录在线延迟的定义。
- `Inference` 的 `queue_time_seconds` 全部为空，符合在线推理不记录训练/批处理排队时间的定义。
- 这两类属于结构性空值，清洗时保留为空，不填 0，也不删除记录。
- GPU、显存利用率和可用性只有少量零散空值，仍需与遥测状态交叉验证。

第四轮交叉验证确认：

- 630 条 GPU 利用率空值和 398 条显存利用率空值全部来自 `partial` 遥测；全部 1,028 条 `partial` 记录至少缺少一项核心指标。
- 239 条可用性空值全部来自 `late` 遥测。
- `complete` 记录没有上述核心指标空值。

这些空值是遥测质量状态的真实表达。清洗层应保留空值和状态，不应填 0；计算利用率或可用性时，只使用对应指标非空的记录，并同时报告数据覆盖率。

账单字段按费用类型拆分后：

- 84 条 `Support` 和 2 条 `Credit` 不带资源池，符合共享支持费和供应商抵扣的计费特点。
- 43 条 `Adjustment`、2 条 `Credit`、84 条 `Support` 不带 GPU 小时和单价，属于非用量费用的合理空值。
- 42 条团队标签缺失分布在 `Usage`（27 条）与 `UnusedCommitment`（15 条），仍需结合资源池和采购方式判断能否回填归属。
- 420 条合同空值中，`Usage` 占 312 条；是否合理需继续按采购方式拆分。

第四轮确认全部 42 条团队缺失账单都有非空资源池，且均能通过标准化资源池 ID 从资源清单推导团队。清洗层可以生成 `attributed_team_id`，优先使用账单团队，缺失时使用资源清单团队，同时保留原始 `team_id` 和回填来源标记。

合同空值与采购方式完全一致：288 条 `OnDemand` 和 132 条 `Owned` 记录没有合同；473 条 `Reserved` 和 316 条 `SavingsPlan` 记录全部有合同。承诺采购缺合同和非合同采购误带合同均为 0，因此 420 条合同空值均为结构性空值。

### 2.4 类型与账单算术

- 非空显存利用率转换失败：0。

### 2.7 时间口径

终端以 Asia/Shanghai 时区显示：

- 首条：`2025-08-01 08:00:00+08`
- 末条：`2026-08-01 07:00:00+08`
- 本地月份数：13

这并不证明原始 UTC 数据覆盖 13 个月。UTC 区间跨越 12 个完整月份，但转换到 `+08` 后，最后 8 个小时落入本地 8 月。设置会话时区为 UTC 后复核：

- 首条：`2025-08-01 00:00:00+00`
- 末条：`2026-07-31 23:00:00+00`
- UTC 月份数：12

正式月度分析必须显式设置 UTC，避免按本机时区切月。

### 2.10 事件空值解释

缺少团队和产品的记录为 `EVT-014`，类型为 `Pricing`，描述为云厂商更新亚太区域 GPU 价目表，区域为 `ap-southeast-1`。该事件描述的是区域供应商价格变化，不限定单一团队或产品，因此当前判断为空值合理。

### 2.11 重复内容验证

139 组重复 `usage_record_id` 的非 ID 字段内容全部一致，冲突组为 0。因此这 139 组属于完全重复，可在清洗视图中每组保留一行。

另有 120 组不同记录 ID 的业务重复，全部为 `complete`，内容均不完全相同。进一步检查发现：

- 每组恰好包含一条原始 ID 和一条以 `-R` 结尾的修订 ID；
- 120 组均只有 `gpu_utilization_pct` 不同；
- 其他关键业务指标均相同。

因此 `-R` 可解释为同一小时遥测的修订版本。清洗层对这 120 组保留 `-R` 行，并记录修订去重规则；原始层不删除任何行。

### 2.12 枚举值

本轮列出的使用负载、遥测状态、账单费用类型和采购方式均在数据字典允许范围内，未发现大小写或拼写异常。允许值集合并不要求每个值都必须出现在数据中，因此本期未出现 `Commitment` 不能仅凭这一点判定为错误。

## 4. 审计形成的清洗规则

1. 原始 CSV 保持不变，所有处理生成新的清洗结果。
2. ID 使用 `TRIM`、大写和下划线转连字符生成标准化字段，同时保留原始 ID。
3. 相同 `usage_record_id` 的完全重复每组保留一行。
4. 同一资源池同一小时存在原始行与 `-R` 修订行时，保留 `-R` 行。
5. 延迟、排队、合同及非用量账单字段的结构性空值保持为空。
6. `partial` 和 `late` 遥测空值不填 0；指标计算排除对应空值，并报告有效记录覆盖率。
7. 账单原始团队缺失时，通过标准化资源池 ID 生成归属团队，并增加归属来源字段。
8. 月度时间分析固定使用 UTC。
9. `UnusedCommitment` 不与承诺费用重复计入总账成本。

本轮数据审计已经为进入清洗阶段提供足够规则。SLA 是否达标、成本是否异常属于后续业务分析，不属于基础数据审计。
