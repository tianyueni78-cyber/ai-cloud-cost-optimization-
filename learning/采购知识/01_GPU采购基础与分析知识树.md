# 项目所需GPU采购知识树

## 使用范围

本项目要帮助云基础设施负责人调整按需采购、预留采购和节省计划的组合，同时保护 SLA 和未来业务容量。因此只学习能支持以下判断的知识：

1. 三种采购方式及自有资源在成本与灵活性上的差别；
2. 每种采购方式花了多少钱、占比多少；
3. 承诺采购是否过量，按需采购是否长期买贵；
4. 哪部分稳定需求可能改用承诺采购；
5. 哪些容量在 SLA、增长、型号、区域和合同约束下可以调整。

暂不展开云厂商全部产品条款、会计准则、硬件采购流程和与本项目决策无关的理论。真实合同细节只在分析需要时查证。

## 一、项目分析骨架

```text
采购分析
├─ 花了多少钱 → 账单事实
├─ 为什么这样收费 → 采购方式 + 费用类型
├─ 买了或配置了什么 → 资源清单
├─ 实际用了多少 → 资源使用
├─ 能不能减少 → SLA + 备用容量 + 未来增长
└─ 为什么发生变化 → 价格、业务量、结构、效率、事件
```

以后遇到采购问题，第一步不是猜表名，而是先判断它属于这六个分支中的哪一个。

## 二、四种采购方式

| 中文名称 | 数据中的英文值 | 核心机制 | 主要优点 | 主要风险 | 常见适用场景 |
|---|---|---|---|---|---|
| 按需采购 | `OnDemand` | 实际使用时按当期价格付费，不做长期承诺 | 灵活，适合快速扩缩 | 单价通常较高 | 临时训练、突发流量、新业务试运行 |
| 预留采购 | `Reserved` | 对特定期限、容量或使用量作出承诺，换取折扣 | 稳定负载通常更便宜 | 买多后仍需承担承诺成本 | 长期稳定的生产推理或基础训练容量 |
| 节省计划 | `SavingsPlan` | 承诺一定期限内的消费水平，符合规则的使用获得折扣 | 通常比固定预留更灵活 | 承诺仍可能过量，覆盖受合同规则限制 | 总消费较稳定、资源组合会变化的负载 |
| 自有资源 | `Owned` | 公司持有设备，成本来自折旧、托管、电力等口径 | 控制力强，稳定负载可能有优势 | 扩缩慢，固定成本和维护责任较高 | 长期核心负载、数据或合规要求较高的场景 |

以上是通用机制。真实项目必须再查看合同期限、折扣、最低承诺、覆盖范围，以及是否绑定区域、型号或服务。

## 三、采购方式与费用类型不是一回事

```text
采购方式 procurement_model
→ 回答：资源通过什么购买机制获得？

费用类型 charge_type
→ 回答：这一行账单为什么收费、抵扣或调整？
```

一条账单可以同时具有两个分类。例如：

```text
采购方式 = 预留采购（Reserved）
费用类型 = 承诺费用（Commitment）
```

所以，分析采购组合时按采购方式分组；定义总账纳入范围或核对账单时看费用类型。不能用其中一个替代另一个。

本项目常见费用类型：

| 中文含义 | 英文值 | 分析作用 |
|---|---|---|
| 使用费用 | `Usage` | 实际用量产生的费用 |
| 承诺费用 | `Commitment` | 采购承诺产生的费用 |
| 抵扣 | `Credit` | 冲减费用，注意金额符号和账单规则 |
| 调整 | `Adjustment` | 更正、补记或其他调整 |
| 支持费用 | `Support` | 相关支持服务费用，可能无法直接归到资源池 |
| 未使用承诺 | `UnusedCommitment` | 已承诺但未被利用的部分；作为浪费信号单独展示，不能在已计承诺费用上再次相加 |

## 四、五张表在采购分析中的职责

| 想回答的问题 | 首选表 | 原因 |
|---|---|---|
| 公司、团队或采购方式花了多少钱 | `cloud_billing` | 一行是一条费用事实，并含净成本 |
| 当前有哪些GPU、多少张、怎样采购 | `resource_inventory` | 一行描述一个资源池的配置和生命周期 |
| GPU实际有多忙、承载多少业务 | `resource_usage` | 一行描述某资源池某小时的使用与业务表现 |
| 容量能否减少而不破坏服务 | `team_sla` + `resource_usage` | 必须把实际表现与目标、备用要求比较 |
| 某月为什么突增或下降 | 前述事实表 + `business_events` | 事件帮助提出解释，但不能单独证明因果 |

记忆骨架：

```text
问钱先找账单，问资产先找清单，问忙闲先找使用，
问能否回收要看SLA，问为何变化再查事件。
```

“先找”指先选主表，不代表永远只用一张表。只有主表缺少回答问题所需的信息时才关联。

## 五、常见采购问题、公式与数据动作

### 1. 每种采购方式花了多少钱

```text
某采购方式成本
= Σ 该采购方式下符合总账口径的 net_cost_usd
```

数据动作：账单表按 `procurement_model` 分组，把 `net_cost_usd` 求和。

### 2. 每种采购方式占总成本多少

```text
采购方式成本占比
= 某采购方式成本 ÷ 同口径GPU账单总成本 × 100%
```

先算各采购方式小计，再除以同一期间、同一费用口径的总计。

### 3. 按需采购是否买贵

```text
按需成本率
= 按需采购成本 ÷ 同口径GPU账单总成本 × 100%
```

高占比只是线索，不是结论。还要查看：负载是否长期稳定、峰值是否短暂、业务是否仍在快速增长、承诺合同是否有空间。突发需求使用按需采购可能是合理的。

### 4. 承诺是否买多

在缺少合同承诺小时字段时，可使用金额代理：

```text
未使用承诺成本率
= UnusedCommitment金额 ÷ Commitment金额 × 100%
```

它不是物理容量利用率。应按合同、月份、区域或适用范围分层，不能只看公司总平均。

### 5. 能否把按需采购转成承诺采购

逻辑条件：

```text
长期稳定需求
+ 已满足SLA的安全余量
+ 未来增长仍需要的容量
→ 才可能成为承诺采购候选
```

账单表用来估算成本差异；资源使用表判断需求是否稳定；SLA表限制最低安全容量。单靠按需单价高，不能决定转换。

### 6. 能否减少GPU资源

概念公式：

```text
可优化容量
= 当前可用容量
- 业务需求容量
- SLA要求的备用容量
- 已确认的未来增长容量
```

还要检查型号兼容、地区、容灾角色、合同期限和迁移可行性。低利用率不等于可直接回收。

## 六、固定判断顺序

```text
1. 问题在问钱、资产、使用、约束，还是原因？
2. 选择直接记录这个事实的主表。
3. 检查分组字段和数值字段是否已经在主表。
4. 已经存在 → 不关联，直接筛选、分组和计算。
5. 确实缺少 → 再关联补信息，并检查键、粒度和有效期。
6. 关联前后核对行数、未匹配数和核心总额。
7. 最后再结合SLA、合同和增长约束提出行动。
```

### 典型错误

问题：比较三种采购方式各花了多少钱。

错误选择：直接使用资源清单。资源清单描述“配置了什么”，不记录公司实际承担的每条净账单费用。

正确选择：账单表已经包含采购方式与净成本，因此按采购方式分组，把净成本求和；不需要为了这个基础问题先连接资源清单。

## 七、完成检查

面对新的采购问题时，能回答以下问题才开始写代码：

1. 它主要问钱、资产、使用、约束还是原因？
2. 主表为什么能直接记录这个事实？
3. 完整公式是什么？
4. 按什么维度分组，计算哪个数值？
5. 是否真的需要关联？缺的具体信息是什么？
6. 采购方式、费用类型和时间口径是否混淆？
7. 结果只是异常线索，还是足以支持采购行动？
