# 02｜理解业务问题

## 本阶段通用公式

```text
决策者 + 待决定的行动 + 衡量指标 + 业务约束 + 时间范围
= 可分析的业务问题
```

| 固定部分：任何项目都要回答 | 变化部分：必须重新调查 |
|---|---|
| 谁使用分析结果、要做什么决定 | 公司商业模式和利益相关者 |
| 成功用什么指标衡量 | KPI 的具体名称、公式和单位 |
| 哪些约束不能被优化掉 | SLA、法规、合同、预算和战略要求 |
| 分析时间范围和比较基准是什么 | 财年、活动周期、季节性和基准期 |
| 哪些结论属于事实、假设或建议 | 当前管理层优先级和风险偏好 |

标准输入通常是业务背景、访谈、指标定义、合同或政策；标准输出是问题定义、指标口径、约束清单，而不是 SQL 查询。完成标准是每个分析问题都能对应一个潜在决策。

本项目只是把变量替换为 AI 云成本、团队、GPU、SLA 和采购合同；上面的公式可以直接迁移到销售、供应链或运营项目。

## 目标

把“云成本太高”转换成可以用数据回答的问题，避免一开始就盲目计算。

## 使用软件与输入

- 软件：GitHub 浏览器或 VS Code。
- 输入：`README.md`、`docs/company_background.md`、`docs/data_dictionary.md`、`workbook.md`。
- 输出：新建 `reports/business_understanding.md`。

## 操作步骤

### 1. 写一句项目目标

使用结构：

```text
帮助【决策者】在【业务限制】下决定【行动】，衡量指标为【指标】。
```

不要只写“分析 GPU 数据”。目标必须包含决策。

### 2. 建立业务实体表

在报告中整理：

| 实体 | 需要记录什么 |
|---|---|
| 公司 | 商业模式、区域和管理目标 |
| 产品 | 产品 ID、收入方式和主要负载 |
| 团队 | 团队 ID、职责和成本责任 |
| 资源 | GPU、采购方式、区域和用途 |
| SLA | 可用性、延迟、备用容量和恢复要求 |
| 事件 | 发布、客户、事故、迁移和采购 |

### 3. 区分利益相关者

| 角色 | 典型关注点 |
|---|---|
| CFO | 总成本、预算、承诺浪费、可实现节省 |
| CTO | 容量、性能、架构迁移和技术风险 |
| 团队负责人 | 业务增长、资源需求和 SLA |
| FinOps/分析师 | 口径、归因、预测和行动跟踪 |

同一个指标可能有不同解释。例如低利用率对 CFO 是成本问题，对 CTO 可能是容灾保障。

### 4. 将模糊问题拆成分析问题

```text
“成本为什么上涨？”
├── 业务量是否上涨？
├── 单位业务成本是否上涨？
├── GPU 规格是否变贵？
├── 采购方式是否改变？
├── 共享费用或调整项是否增加？
└── 使用月份与发票月份是否错位？
```

### 5. 记录约束

从文档中提取但不要自行发明：

- SLA 和故障恢复；
- 数据驻留和区域限制；
- 合同期限；
- GPU 兼容性；
- 容量交付提前期；
- 业务发布日期。

### 6. 建立指标草案

此时只定义概念，不计算数值：

| 指标 | 需要回答的问题 |
|---|---|
| 月度净成本 | 每月实际费用如何变化？ |
| GPU 利用率 | 分配容量被使用到什么程度？ |
| 单位成本 | 每单位可比较业务量消耗多少成本？ |
| 承诺覆盖 | 多少使用由长期承诺覆盖？ |
| SLA 达标率 | 服务表现是否满足要求？ |

## 思维框架

```text
现象 → 驱动因素 → 业务限制 → 可选行动 → 收益与风险
```

## 验收标准

- 能区分团队、产品、资源和负载。
- 写明谁需要做什么决策。
- 至少列出成本、容量、效率和 SLA 四类问题。
- 记录业务限制，不把低利用率直接视为浪费。
- 没有提前写数据结论。
