# 指标与数据映射

这份文档解决一个问题：**知道业务要什么，但不知道应选哪些表、字段、公式和规则。**

它不是术语词典。每个指标都按同一条链路设计：

```text
业务场景 → 决策 → 指标定义 → 完整公式 → 数据映射
→ 时间与粒度 → 场景分支 → 常见错误 → 验证
```

日常推进项目看[九阶段模板](数据分析九阶段填空模板.md)；卡在公式、表、字段、关联、时间或粒度时再打开本页。

---

## 一、先填写指标映射卡

```text
业务问题：【要支持什么决定】
指标名称：【】
业务含义：【它衡量什么，不是由什么解释】
指标类型：【总量 / 数量 / 比例 / 达标 / 效率 / 变化 / 容量】
完整公式：【包含分子、分母、筛选和比较条件】
事实数据：【表.字段】
目标或规则：【表.字段 / 不适用】
关联键：【ID + 必要的生效时间】
来源粒度：【源表一行代表什么】
输出粒度：【结果一行代表什么】
主时间口径：【】
单位及不可混合项：【】
纳入 / 排除规则：【】
验证方法：【怎样证明没有重复、漏算或错误连接】
可支持的行动：【】
```

### 为什么必须先填

字段名相似不代表业务含义相同。例如：

- `gpu_utilization_pct` 衡量资源繁忙程度，不能定义账单成本；
- `invoice_month` 是入账月份，不一定是资源使用月份；
- `UnusedCommitment` 是管理展示口径，和 `Commitment` 同时进入总账会重复；
- `requests`、`jobs`、`k_pages` 都是业务量，但不能相加。

## 二、五张表分别扮演什么角色

| 表 | 一行代表什么 | 角色 | 主要回答 |
|---|---|---|---|
| `resource_inventory` | 一个GPU资源池 | 资源/维度表 | 有什么资源、归谁、在哪里、怎样采购 |
| `resource_usage` | 一个资源池一个UTC小时 | 运营事实表 | 如何使用、承载多少业务、服务表现如何 |
| `cloud_billing` | 一条账单费用记录 | 财务事实表 | 实际产生了什么费用 |
| `team_sla` | 一条带生效期的SLA规则 | 规则表 | 什么才算达标、最低要保留多少容量 |
| `business_events` | 一项业务或技术事件 | 上下文表 | 指标变化可能与什么事件有关 |

通用判断：

```text
要实际值 → 找事实表
要目标值 → 找规则表
要对象属性 → 找维度或清单表
要解释变化 → 找事件表，但事件不是因果证明
```

## 三、这个项目的关联地图

### 1. 使用记录连接资源清单

```text
resource_usage.resource_pool_id_normalized
→ resource_inventory.resource_pool_id_normalized

关系：多条资源小时 → 一个资源池
```

用途：补充GPU型号、区域、采购方式、环境和容灾角色。

验证：连接前后使用表行数不应增加；标准化后资源池关联率应达到预期。

### 2. 账单连接资源清单

```text
cloud_billing.resource_pool_id_normalized
→ resource_inventory.resource_pool_id_normalized

关系：多条账单行 → 一个资源池
```

用途：把可直接归属的费用映射到团队、产品、GPU型号和区域。

场景分支：`Support` 等共享费用可能没有资源池，必须使用 `LEFT JOIN` 保留。连接前后总金额必须一致。

### 3. 使用记录连接SLA

```text
team_id + product_id + workload_type + region
+ timestamp落在effective_from与effective_to之间
```

只按团队连接是错的：同一团队在不同产品、负载、地区和生效期可能适用不同规则。

### 4. 账单连接使用数据

不能把月度账单直接连接几十万条小时记录，否则账单会被重复放大。正确顺序：

```text
账单 → 汇总到资源池月
使用 → 汇总到资源池月
两份月表 → 按资源池月连接
```

### 5. 事件连接指标

```text
事件时间范围 + 可用的团队/产品/区域
→ 对应范围的月度或小时指标
```

事件只能形成待验证假设。还要比较事件前后、正常周期和未受影响对象。

## 四、时间、粒度和单位

### 时间场景

| 要回答的问题 | 使用时间 |
|---|---|
| 资源什么时候被使用 | `timestamp_utc` |
| 成本对应哪个业务期间 | `usage_start_date`—`usage_end_date` |
| 财务在哪个月看到费用 | `invoice_month` |
| 数据什么时候入内部系统 | `recorded_at` |
| 当时适用哪条SLA | `effective_from`—`effective_to` |
| 当时资源是否有效 | `start_date`—`end_date` |
| 事件在什么时候影响业务 | `start_timestamp_utc`—`end_timestamp_utc` |

### 来源粒度与输出粒度

```text
来源粒度：源表一行代表什么
输出粒度：分析结果一行代表什么
```

例如账单来源粒度是一条费用记录，但成本趋势输出粒度通常是公司月或团队月。关联前必须把两侧统一到可比较粒度。

### 单位规则

- 金额：USD；
- 容量：GPU张数或GPU小时，不能混用；
- 比例：数据中使用0—100，不是0—1；
- 延迟：毫秒；排队：秒；
- 业务量：`requests`、`jobs`、`k_pages` 必须分开。

## 五、场景与完整公式

### 场景1：公司实际花了多少钱

**决策：** 判断成本规模、趋势以及采购组合是否需要调整。

**指标：GPU账单总成本**

```text
GPU账单总成本
= Σ net_cost_usd
其中 charge_type ∈ {Usage, Commitment, Credit, Adjustment, Support}
且 UnusedCommitment 单独展示、不重复计入
```

数据映射：

```text
金额：cloud_billing.net_cost_usd
费用类型：cloud_billing.charge_type
业务期间：usage_start_date、usage_end_date
财务期间：invoice_month
采购结构：procurement_model
```

场景分支：

- 运营视角按使用期间分析；
- 财务视角按发票月份分析；
- `Credit` 和部分 `Adjustment` 可为负；
- `Support` 进入公司总账，但归因时需要分摊。

验证：

```text
billing_line_id无重复
net_cost_usd = gross_cost_usd - discount_usd
各charge_type小计 = 公司总计
连接资源清单前后总额不变
使用期间与发票月份差异能够解释
```

### 场景2：成本集中在哪里

**指标：成本占比**

```text
某分类成本占比
= 该团队/产品/区域/采购方式的总成本
÷ 同一范围内公司总成本
× 100%
```

分子和分母必须使用相同时间、费用和环境口径。各分类占比合计应接近100%；未归属成本必须显式保留。

### 场景3：成本变化多快

**指标：月环比**

```text
月环比增长率
= (本月成本 - 上月成本) ÷ 上月成本 × 100%
```

**指标：同比**

```text
同比增长率
= (本月成本 - 去年同月成本) ÷ 去年同月成本 × 100%
```

只有12个月数据时，无法形成完整同比序列；此时优先使用环比、趋势和情景，不伪造同比结论。

### 场景4：GPU到底忙不忙

可以使用两种口径，不能混称：

```text
容量活跃率
= Σ active_gpu_count ÷ Σ allocated_gpu_count × 100%
```

```text
加权遥测利用率
= Σ(gpu_utilization_pct × allocated_gpu_count)
÷ Σ allocated_gpu_count
```

第一种关注活跃容量，第二种关注核心遥测。简单平均各资源池百分比会让小资源池和大资源池权重相同。

低利用率不是自动浪费：`WarmStandby`、`DR`、P0服务、数据驻留和研发发布时间都可能要求保留容量。

### 场景5：每单位业务花多少钱

```text
推理单位成本 = 推理可归属成本 ÷ requests
训练单位成本 = 训练可归属成本 ÷ jobs
文档单位成本 = 文档可归属成本 ÷ k_pages
```

先完成成本归因，再计算单位成本。不同 `volume_unit` 不得合并成一个公司平均值。

### 场景6：服务是否达到SLA

**通用公式：**

```text
SLA达标率
= 达到适用SLA规则的可判断对象数
÷ 具有有效SLA且实际指标可计算的对象总数
× 100%
```

适用规则：

```text
Inference可用性达标：月度实际可用性 ≥ availability_target_pct
Inference延迟达标：约定粒度的P95延迟 ≤ p95_latency_target_ms
Training/Batch排队达标：queue_time_seconds ≤ max_queue_time_seconds
```

数据映射：

```text
实际：resource_usage.availability_pct、p95_latency_ms、queue_time_seconds
目标：team_sla.availability_target_pct、p95_latency_target_ms、max_queue_time_seconds
```

注意：使用表是小时粒度，可用性目标是月度口径。必须先形成月度实际值再比较。小时P95如何汇总成月度SLA不能擅自平均；若业务规则未定义，应标记待确认或采用明确说明的保守代理。

### 场景7：还有多少安全容量

```text
最低备用GPU数
= 总GPU容量 × min_spare_capacity_pct ÷ 100
```

```text
安全可投入容量
= 总GPU容量 - 最低备用GPU数
```

```text
当前容量余量
= 安全可投入容量 - 峰值已分配GPU数
```

数据映射：

```text
总容量：resource_inventory.gpu_count
已分配：resource_usage.allocated_gpu_count
活跃容量：resource_usage.active_gpu_count
最低备用比例：team_sla.min_spare_capacity_pct
```

不同GPU型号不能只按张数等价替换；计算结果还要按型号、区域、负载和兼容性分层。

### 场景8：采购承诺是否买多

如果没有合同承诺GPU小时字段，只能计算金额代理指标：

```text
未使用承诺成本率（金额代理）
= UnusedCommitment金额
÷ Commitment金额
× 100%
```

它不是物理容量利用率。真正的承诺利用率还需要合同承诺小时或金额覆盖规则，数据不足时必须说明限制。

### 场景9：共享费用归给谁

```text
对象分摊权重
= 对象驱动量 ÷ 所有对象驱动量
```

```text
对象共享费用
= 共享费用 × 对象分摊权重
```

驱动量可以是活跃GPU小时、分配GPU小时、可比较业务量或直接成本。选择标准是能否代表资源消耗或业务责任，而不是哪个字段最方便。

对账：分摊前共享费用必须等于分摊后各对象费用之和。

### 场景10：成本为什么变化

可解释框架：

```text
成本
= 业务量
× 单位业务所需GPU小时
× 每GPU小时有效费率
```

实际变化还会受到采购结构、GPU型号、区域、产品结构和一次性调整影响。

分析顺序：

```text
总变化
→ 业务量效应
→ 资源效率效应
→ 价格/折扣效应
→ 采购和产品结构效应
→ 一次性事件
```

事件与变化同期只构成相关证据；需要范围匹配、前后比较和替代解释检查。

### 场景11：未来需要多少容量

```text
单位业务容量消耗
= 活跃GPU小时 ÷ 同单位业务量
```

```text
未来工作容量需求
= 未来业务量预测 × 单位业务容量消耗
```

```text
未来总容量需求
= 未来工作容量需求 ÷ (1 - 最低备用容量率)
```

必须分别预测 `requests`、`jobs` 和 `k_pages`，并按GPU型号、区域和工作负载校验可替代性。

### 场景12：优化行动值不值得做

```text
年度毛节省
= 当前基线年度成本 - 优化后年度成本
```

```text
首年净收益
= 年度毛节省 - 一次性实施成本 - 首年新增运行成本
```

```text
回收期（月）
= 一次性实施成本 ÷ 月度净节省
```

优先级不能只按节省额排序，还要同时考虑SLA、合同到期、迁移难度、容量风险和证据可信度。

## 六、映射完成检查

- 指标含义没有写成它的解释变量；
- 公式包含分子、分母、范围和比较条件；
- 每个公式项都能找到表和字段，缺失数据已明确；
- 关联键包含必要的复合字段和生效期；
- 来源粒度与输出粒度已经区分；
- 时间口径与业务问题一致；
- 单位能够比较，不能混合的对象已分组；
- 纳入、排除和分摊规则有业务依据；
- 连接和聚合后能够对账；
- 指标结果能够对应一个可执行行动。

如果任一项不成立，先修正映射，不要急着写SQL。
