# 指标与数据映射

这份文档解决一个问题：**知道业务要什么，但不知道应选哪些表、字段、公式和规则。**

它不是术语词典。每个指标都按同一条链路设计：

```text
业务场景 → 决策 → 指标定义 → 完整公式 → 数据映射
→ 时间与粒度 → 场景分支 → 常见错误 → 验证
```

日常推进项目看[九阶段模板](数据分析九阶段填空模板.md)；卡在公式、表、字段、关联、时间或粒度时再打开本页。

---

## 一、一指标六定

字段本身可能完全正确，却被放进错误的业务位置。这样的SQL通常能运行，数字也像真的，因此比语法报错更危险。

```text
一定主表
二定来源粒度
三定时间
四定数值
五定规则
六定验证
```

最短口诀：

> 算什么定主表，一行什么定粒度，问的何时定时间，公式什么定数值，业务边界定规则，前后总额做验证。

---

## 二、六定的完整判断规则

### 1. 定主表：这个指标主要描述什么事实

先选一张主事实表，再决定是否需要连接其他表。

| 要分析什么 | 首选主表 | 为什么 |
|---|---|---|
| 成本、账单、折扣、单价、费用类型 | `cloud_billing` | 一行是账单费用事实 |
| GPU使用、利用率、业务量、实际延迟和可用性 | `resource_usage` | 一行是资源池小时运行事实 |
| GPU数量、型号、地区、容灾角色和资源归属 | `resource_inventory` | 一行是一个资源池 |
| SLA目标、优先级、最低备用容量 | `team_sla` | 一行是带生效期的规则 |
| 产品发布、事故、迁移、采购和价格事件 | `business_events` | 一行是业务或技术事件 |

口诀：

```text
算钱找账单
看运行找使用
看家底找清单
判达标找SLA
解释变化找事件
```

表的通用角色：

```text
要实际值 → 找事实表
要目标值 → 找规则表
要对象属性 → 找维度或清单表
要解释变化 → 找事件表，但事件不是因果证明
```

SLA达标需要两种角色配合：实际表现来自 `resource_usage`，目标标准来自 `team_sla`。不能因为最后用了两张表，就跳过主事实表的选择。

### 2. 定来源粒度：主表的一行代表什么

| 表 | 来源粒度 |
|---|---|
| `cloud_billing` | 一条账单费用记录 |
| `resource_usage` | 一个资源池一个UTC小时 |
| `resource_inventory` | 一个GPU资源池 |
| `team_sla` | 一条带生效期的SLA规则 |
| `business_events` | 一项业务或技术事件 |

同时区分输出粒度：

```text
来源粒度 = 原始表的一行代表什么
输出粒度 = 查询结果的一行代表什么
```

例如：

```text
账单来源粒度：一条账单费用记录
公司趋势输出粒度：一个公司一个月
团队趋势输出粒度：一个团队一个月
采购结构输出粒度：一个采购方式一个月
```

连接前必须让两边处于可比较粒度。月度账单直接连接小时使用记录，会让一条账单匹配几十或几百条小时记录，金额被成倍放大。

### 3. 定时间：问题问的是哪一种“什么时候”

原则：

> 时间字段跟着业务问题走，但优先从主事实表中选择。

#### 成本主表

| 问题 | 时间字段 |
|---|---|
| 费用对应哪个实际业务期间 | `usage_start_date`、`usage_end_date` |
| 财务在哪个月看到费用 | `invoice_month` |
| 账单什么时候进入内部系统 | `recorded_at` |

#### 其他表

| 问题 | 表与时间字段 |
|---|---|
| GPU在哪个小时运行 | `resource_usage.timestamp_utc` |
| 当时哪条SLA有效 | `team_sla.effective_from`、`effective_to` |
| 当时资源池是否有效 | `resource_inventory.start_date`、`end_date` |
| 事件什么时候发生和结束 | `business_events.start_timestamp_utc`、`end_timestamp_utc` |

成本指标的主表是 `cloud_billing`，所以分析费用对应的业务期间时使用 `usage_start_date`—`usage_end_date`；分析财务入账时使用 `invoice_month`。`resource_usage.timestamp_utc` 虽然更细，但它属于另一张小时事实表，不能直接拿来代替账单时间。

确实需要跨表时，必须先回答：

```text
为什么要连接？
两边一行分别代表什么？
使用哪些键？
是一对一、多对一还是多对多？
连接前是否先汇总到共同粒度？
连接后行数和控制总额是否变化？
```

错误后果：用发票月解释业务活动可能制造虚假峰值；跨表借小时字段可能迫使错误连接，并放大账单金额。

### 4. 定数值：公式真正计算哪个字段

先问：

```text
SUM里面是什么？
COUNT统计谁？
分子是什么？
分母是什么？
实际值是什么？
目标值是什么？
```

| 指标 | 核心数值字段 |
|---|---|
| 账单总成本 | `net_cost_usd` |
| 计费GPU小时 | `billed_gpu_hours` |
| GPU总容量 | `gpu_count` |
| 已分配容量 | `allocated_gpu_count` |
| 活跃容量 | `active_gpu_count` |
| 业务量 | `business_volume`，同时保留 `volume_unit` |
| 实际可用性 | `availability_pct` |
| 可用性目标 | `availability_target_pct` |
| 实际延迟 | `p95_latency_ms` |
| 延迟目标 | `p95_latency_target_ms` |

字段职责口诀：

```text
数字字段负责计算
分类字段负责分组
ID字段负责关联
时间字段负责范围
规则字段负责判断
```

以成本为例：

```text
net_cost_usd → 数值
procurement_model → 分类
resource_pool_id → 关联
invoice_month → 时间
charge_type → 纳入规则
```

字段都出现在同一条查询中，不代表它们都叫“数值字段”。

### 5. 定规则：什么进入、排除、分开或比较

每个指标至少回答：

```text
纳入什么？
排除或单独展示什么？
哪些对象必须分开？
什么条件才算达标？
```

当前成本：

```text
计入：Usage、Commitment、Credit、Adjustment、Support
单独展示且不重复计入：UnusedCommitment
```

`Commitment` 已经记录承诺费用，`UnusedCommitment` 是其中未被工作负载覆盖部分的管理口径；两者同时相加会重复计算。

当前业务量：

```text
requests、jobs、k_pages分别统计，不能相加
```

当前SLA：

```text
实际可用性 ≥ 可用性目标
实际延迟 ≤ 延迟目标
实际排队时间 ≤ 最大允许排队时间
```

规则必须来自数据字典、业务背景、合同或负责人确认，不能根据字段名现场发明。

### 6. 定验证：怎样主动发现自己算错了

| 风险 | 验证方式 |
|---|---|
| 原始记录重复 | 检查主键或业务键唯一性 |
| 金额字段内部错误 | 检查金额恒等式 |
| 费用类型漏算或重复 | 分类小计与总计对账 |
| JOIN一行匹配多行 | 比较连接前后行数和金额 |
| 内连接丢失记录 | 比较连接前后覆盖率和总额 |
| 使用月与发票月混淆 | 分别按两个时间口径汇总并解释差异 |
| 分类结果漏掉对象 | 分类合计回到公司总计 |
| 比例错误 | 检查分母、适用范围和合理区间 |

口诀：

```text
聚合前查重复
连接前看粒度
连接后查行数
分类后回总计
换时间做对账
```

验证不是计算完成后的装饰，而是为每一种严重错误预先安装报警器。

## 三、五条禁止规则

```text
1. 不跨事实表借核心时间。
2. 不在粒度不同的时候直接JOIN。
3. 不把分类字段当计算数值。
4. 不把目标值当实际表现。
5. 不把事件同期出现当作因果。
```

## 四、常见分析方式与字段组合

| 想怎样拆分 | 一般使用 | 注意 |
|---|---|---|
| 按团队 | `team_id` 或清洗后的 `attributed_team_id` | 明确账单标签与清单回填的优先级 |
| 按产品 | `product_id` | `PRD-SHARED` 可能需要二次分摊 |
| 按GPU型号 | `gpu_model` | 通常通过资源池连接清单 |
| 按采购方式 | `procurement_model` | 成本分析优先使用账单发生时的值 |
| 按区域 | `region` | 账单可能需要通过资源池补充 |
| 按工作负载 | `workload_type` | Training、Inference、Batch指标不同 |
| 按费用类型 | `charge_type` | 用于费用口径和对账 |
| 按月份 | 业务期间或 `invoice_month` | 先说明业务视角还是财务视角 |

同名字段也要看表的职责：

```text
分析账单发生时的采购方式 → cloud_billing.procurement_model
分析资源当前配置的采购方式 → resource_inventory.procurement_model
```

没有“看到同名字段就永远选某一张表”的绝对规则，只有与业务问题、主事实和时间口径一致的选择。

### 单位规则

- 金额使用USD；
- 容量的GPU张数与GPU小时不能混用；
- 百分比字段使用0—100，不是0—1；
- 延迟是毫秒，排队时间是秒；
- `requests`、`jobs`、`k_pages` 必须分开。

## 五、这个项目的关联地图

### 1. 使用记录连接资源清单

```text
resource_usage.resource_pool_id_normalized
→ resource_inventory.resource_pool_id_normalized

关系：多条资源小时 → 一个资源池
```

用途：补充GPU型号、区域、采购方式、环境和容灾角色。

验证：连接前后使用表行数不应增加；标准化后资源池关联率应达到预期。

### 2. 账单连接资源清单

```text
cloud_billing.resource_pool_id_normalized
→ resource_inventory.resource_pool_id_normalized

关系：多条账单行 → 一个资源池
```

用途：把可直接归属的费用映射到团队、产品、GPU型号和区域。

场景分支：`Support` 等共享费用可能没有资源池，必须使用 `LEFT JOIN` 保留。连接前后总金额必须一致。

### 3. 使用记录连接SLA

```text
team_id + product_id + workload_type + region
+ timestamp落在effective_from与effective_to之间
```

只按团队连接是错的：同一团队在不同产品、负载、地区和生效期可能适用不同规则。

### 4. 账单连接使用数据

不能把月度账单直接连接几十万条小时记录。正确顺序：

```text
账单 → 汇总到资源池月
使用 → 汇总到资源池月
两份月表 → 按资源池月连接
```

### 5. 事件连接指标

```text
事件时间范围 + 可用的团队/产品/区域
→ 对应范围的月度或小时指标
```

事件只能形成待验证假设。还要比较事件前后、正常周期和未受影响对象。

## 六、指标映射卡

```text
业务问题：【要支持什么决定】
指标名称：【】
业务含义：【它衡量什么，不是由什么解释】
指标类型：【总量 / 数量 / 比例 / 达标 / 效率 / 变化 / 容量】
主表：【】
完整公式：【包含分子、分母、筛选和比较条件】
事实数据：【表.字段】
目标或规则：【表.字段 / 不适用】
关联键：【ID + 必要的生效时间】
来源粒度：【源表一行代表什么】
输出粒度：【结果一行代表什么】
主时间口径：【】
单位及不可混合项：【】
纳入 / 排除规则：【】
验证方法：【怎样证明没有重复、漏算或错误连接】
可支持的行动：【】
```

字段名相似不代表业务含义相同。例如：

- `gpu_utilization_pct` 衡量资源繁忙程度，不能定义账单成本；
- `invoice_month` 是入账月份，不一定是使用月份；
- `UnusedCommitment` 与 `Commitment` 同时进入总账会重复；
- 三种 `volume_unit` 都是业务量，但不能相加。

## 七、场景与完整公式

### 场景1：公司实际花了多少钱

**决策：** 判断成本规模、趋势以及采购组合是否需要调整。

**指标：GPU账单总成本**（衡量分析期间内，公司因GPU资源使用、采购承诺、
账单抵扣与调整以及相关支持服务实际承担的净账单费用。）

```text
GPU账单总成本
= Σ net_cost_usd
其中 charge_type ∈ {Usage, Commitment, Credit, Adjustment, Support}
且 UnusedCommitment 单独展示、不重复计入
```

数据映射：

```text
金额：cloud_billing.net_cost_usd
费用类型：cloud_billing.charge_type
业务期间：usage_start_date、usage_end_date
财务期间：invoice_month
采购结构：procurement_model
```
```text
来源表：
cloud_billing.csv
来源粒度：
一条账单费用记录
输出粒度：
一个公司一个月
数值字段：
net_cost_usd
```

场景分支：

- 运营视角按使用期间分析；
- 财务视角按发票月份分析；
- `Credit` 和部分 `Adjustment` 可为负；
- `Support` 进入公司总账，但归因时需要分摊。

验证：

```text
billing_line_id无重复
net_cost_usd = gross_cost_usd - discount_usd
各charge_type小计 = 公司总计
连接资源清单前后总额不变
使用期间与发票月份差异能够解释
```

### 场景2：成本集中在哪里

**指标：成本占比**

```text
某分类成本占比
= 该团队/产品/区域/采购方式的总成本
÷ 同一范围内公司总成本
× 100%
```

分子和分母必须使用相同时间、费用和环境口径。各分类占比合计应接近100%；未归属成本必须显式保留。

### 场景3：成本变化多快

**指标：月环比**

```text
月环比增长率
= (本月成本 - 上月成本) ÷ 上月成本 × 100%
```

**指标：同比**

```text
同比增长率
= (本月成本 - 去年同月成本) ÷ 去年同月成本 × 100%
```

只有12个月数据时，无法形成完整同比序列；此时优先使用环比、趋势和情景，不伪造同比结论。

### 场景4：GPU到底忙不忙

可以使用两种口径，不能混称：

```text
容量活跃率
= Σ active_gpu_count ÷ Σ allocated_gpu_count × 100%
```

```text
加权遥测利用率
= Σ(gpu_utilization_pct × allocated_gpu_count)
÷ Σ allocated_gpu_count
```

第一种关注活跃容量，第二种关注核心遥测。简单平均各资源池百分比会让小资源池和大资源池权重相同。

低利用率不是自动浪费：`WarmStandby`、`DR`、P0服务、数据驻留和研发发布时间都可能要求保留容量。

### 场景5：每单位业务花多少钱

```text
推理单位成本 = 推理可归属成本 ÷ requests
训练单位成本 = 训练可归属成本 ÷ jobs
文档单位成本 = 文档可归属成本 ÷ k_pages
```

先完成成本归因，再计算单位成本。不同 `volume_unit` 不得合并成一个公司平均值。

### 场景6：服务是否达到SLA

**通用公式：**

```text
SLA达标率
= 达到适用SLA规则的可判断对象数
÷ 具有有效SLA且实际指标可计算的对象总数
× 100%
```

适用规则：

```text
Inference可用性达标：月度实际可用性 ≥ availability_target_pct
Inference延迟达标：约定粒度的P95延迟 ≤ p95_latency_target_ms
Training/Batch排队达标：queue_time_seconds ≤ max_queue_time_seconds
```

数据映射：

```text
实际：resource_usage.availability_pct、p95_latency_ms、queue_time_seconds
目标：team_sla.availability_target_pct、p95_latency_target_ms、max_queue_time_seconds
```

注意：使用表是小时粒度，可用性目标是月度口径。必须先形成月度实际值再比较。小时P95如何汇总成月度SLA不能擅自平均；若业务规则未定义，应标记待确认或采用明确说明的保守代理。

### 场景7：还有多少安全容量

```text
最低备用GPU数
= 总GPU容量 × min_spare_capacity_pct ÷ 100
```

```text
安全可投入容量
= 总GPU容量 - 最低备用GPU数
```

```text
当前容量余量
= 安全可投入容量 - 峰值已分配GPU数
```

数据映射：

```text
总容量：resource_inventory.gpu_count
已分配：resource_usage.allocated_gpu_count
活跃容量：resource_usage.active_gpu_count
最低备用比例：team_sla.min_spare_capacity_pct
```

不同GPU型号不能只按张数等价替换；计算结果还要按型号、区域、负载和兼容性分层。

### 场景8：采购承诺是否买多

如果没有合同承诺GPU小时字段，只能计算金额代理指标：

```text
未使用承诺成本率（金额代理）
= UnusedCommitment金额
÷ Commitment金额
× 100%
```

它不是物理容量利用率。真正的承诺利用率还需要合同承诺小时或金额覆盖规则，数据不足时必须说明限制。

### 场景9：共享费用归给谁

```text
对象分摊权重
= 对象驱动量 ÷ 所有对象驱动量
```

```text
对象共享费用
= 共享费用 × 对象分摊权重
```

驱动量可以是活跃GPU小时、分配GPU小时、可比较业务量或直接成本。选择标准是能否代表资源消耗或业务责任，而不是哪个字段最方便。

对账：分摊前共享费用必须等于分摊后各对象费用之和。

### 场景10：成本为什么变化

可解释框架：

```text
成本
= 业务量
× 单位业务所需GPU小时
× 每GPU小时有效费率
```

实际变化还会受到采购结构、GPU型号、区域、产品结构和一次性调整影响。

分析顺序：

```text
总变化
→ 业务量效应
→ 资源效率效应
→ 价格/折扣效应
→ 采购和产品结构效应
→ 一次性事件
```

事件与变化同期只构成相关证据；需要范围匹配、前后比较和替代解释检查。

### 场景11：未来需要多少容量

```text
单位业务容量消耗
= 活跃GPU小时 ÷ 同单位业务量
```

```text
未来工作容量需求
= 未来业务量预测 × 单位业务容量消耗
```

```text
未来总容量需求
= 未来工作容量需求 ÷ (1 - 最低备用容量率)
```

必须分别预测 `requests`、`jobs` 和 `k_pages`，并按GPU型号、区域和工作负载校验可替代性。

### 场景12：优化行动值不值得做

```text
年度毛节省
= 当前基线年度成本 - 优化后年度成本
```

```text
首年净收益
= 年度毛节省 - 一次性实施成本 - 首年新增运行成本
```

```text
回收期（月）
= 一次性实施成本 ÷ 月度净节省
```

优先级不能只按节省额排序，还要同时考虑SLA、合同到期、迁移难度、容量风险和证据可信度。
