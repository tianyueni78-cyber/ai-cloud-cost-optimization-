# 数据分析九阶段填空模板

这份文档是项目的主操作手册。不要一次读完；只打开当前阶段，填写模板，运行，验证，再进入下一阶段。

遇到公式、表、字段、关联、时间或粒度问题，查[指标与数据映射](指标与数据映射.md)。遇到具体语法问题，再查 [SQL](references/sql_reference.md)、[Pandas](references/pandas_reference.md) 或 [Power BI](references/power_bi_reference.md) 速查。

## 固定工作流

```text
明确业务决定 → 填当前阶段工作卡 → 完成指标与数据映射
→ 替换代码占位符 → 运行 → 描述结果 → 验证 → 形成交付物
```

规则：

1. `【】` 中是需要替换的内容；不知道就写“待验证”。
2. 业务规则来自背景、数据字典、合同或负责人，不能从字段名猜出来。
3. 原始数据只读；清洗结果写入新目录。
4. 不把空值自动填0，不把相关性写成因果。
5. 每一阶段达到完成标准后再向下走。

# 1｜业务理解

## 思路

先回答“谁要根据分析做什么决定”，再确定指标。这个阶段通常不写SQL。

## 模板

```text
帮助【一个决策者】
在【至少两个业务约束】下，
决定【至少三个可执行行动】，
从而改善【一个核心指标】，
同时保护【一至两个保护指标】。
分析范围为【明确时间 + 数据实际覆盖的业务范围】。
```

```text
核心指标：【】
业务含义：【它衡量什么】
保护指标：【】
比较基准：【上期 / 预算 / 目标 / 其他】
分析结果要支持的行动：【】
```

## 映射检查

```text
现有数据能否计算核心指标：【是 / 否 / 待验证】
现有数据能否计算保护指标：【是 / 否 / 待验证】
时间和业务范围是否在数据覆盖内：【是 / 否 / 待验证】
决策者是否有权实施这些行动：【是 / 否 / 待确认】
```

## 避坑

- “降低成本”“提高效率”是结果，不是行动；
- 不把所有好指标都列为核心指标；
- 不写数据中不存在的地区、客户或时间范围；
- 不选择当前决策者无权实施的行动；
- 数据不支持的指标写“待补充数据”，不假装能算。

## 完成标准

- 一句话能说清决策者、行动、指标、约束和范围；
- 每个指标都能对应数据或明确的数据缺口；
- 输出：项目目标、指标口径、约束清单。

- 文件名不是粒度，必须查看业务含义和样例；

# 3｜数据审计

## 思路

审计不是“发现空值就删除”，而是量化问题、判断业务含义、评估影响，再决定处理。

```text
结构 → 完整性 → 唯一性 → 有效性 → 一致性 → 关联性 → 时间性
```

## 先找到规则，不能凭数据猜规则

规则来源按优先级查找：

1. 法律、监管、安全和数据驻留要求；
2. 合同、云厂商计费规则和正式SLA；
3. 公司业务规则、数据字典和指标口径；
4. 数据库约束、权威主数据表和接口定义；
5. 历史数据分布只能提示异常，不能单独证明合规。

如果文档没有明确规则，应标记“待业务确认”，不能把观察到的多数情况直接写成正式规则。规则冲突时采用更高优先级来源，并记录来源、版本和生效时间。

## 审计判断顺序

```text
定义规则 → 写出违规条件 → 统计数量 → 查看样例
→ 补充业务上下文 → 分类 → 决定处理 → 清洗后复验
```

常见检查及违规表现：

| 检查 | 合规标准 | 常见违规或例外 |
|---|---|---|
| 唯一性 | 主键唯一；业务键按版本规则唯一 | 完全重复、重试写入、合法修订、连接放大 |
| 完整性 | 必填字段非空；条件必填满足条件 | 真缺失、结构性空值、采集延迟、字段不适用 |
| 有效性 | 数值范围、枚举、格式符合规则 | 越界、非法枚举、单位错误、ID格式噪声 |
| 一致性 | 跨字段公式和条件规则成立 | 金额公式不平、采购方式与合同矛盾、状态与空值矛盾 |
| 关联性 | 外键能匹配权威表，连接不改变总量 | 真正孤儿记录、格式不一致、维表重复导致一对多放大 |
| 时间性 | 时间格式、范围、时区和生效期正确 | 延迟入账、跨月、时区跨日、使用了失效规则 |
| 对账 | 清洗或连接前后关键总量保持可解释 | 漏行、重复计算、金额放大、错误抵扣 |

异常最终只归入以下处理类别：

- **真实错误**：修复、可靠回填、去重或隔离；
- **结构性空值**：保留为空，并保留解释它的状态或业务字段；
- **可接受噪声**：标准化或单独标记，不删除有效记录；
- **合法修订/延迟**：按版本或到达规则处理；
- **待确认**：保留原值，记录风险并向规则负责人确认。

项目示例：`Reserved`、`SavingsPlan` 需要合同编号，`OnDemand`、`Owned` 不要求合同编号。因此不能只检查 `contract_id IS NULL`，必须同时检查 `procurement_model`。规则依据见 [数据字典与业务规则](../docs/data_dictionary.md)。

## SQL骨架

本项目直接读取CSV，因此 `FROM` 后必须使用 `read_csv_auto('【CSV路径】')`。如果换成数据库项目，才把整个读取表达式替换为 `schema.table_name`。

```sql
-- 重复
SELECT
    【候选主键】, -- 例：resource_pool_id；复合主键需在SELECT和GROUP BY中使用同一组字段
    COUNT(*) AS row_count
FROM read_csv_auto('【CSV路径】') -- 只替换【CSV路径】四字并保留单引号；完整例：read_csv_auto('data/resource_inventory.csv')
GROUP BY 【候选主键】             -- 必须与SELECT中的候选主键完全一致
HAVING COUNT(*) > 1;

-- 空值
SELECT COUNT(*) AS total_rows,
       COUNT(*) FILTER (WHERE 【字段】 IS NULL) AS missing_rows
FROM read_csv_auto('【CSV路径】'); -- 完整例：read_csv_auto('data/resource_inventory.csv')

-- 范围
SELECT MIN(TRY_CAST(【字段】 AS DOUBLE)) AS minimum,
       MAX(TRY_CAST(【字段】 AS DOUBLE)) AS maximum
FROM read_csv_auto('【CSV路径】'); -- 完整例：read_csv_auto('data/resource_inventory.csv')

-- 关联率
WITH source AS (
    SELECT * FROM read_csv_auto('【来源CSV路径】') -- 例：'data/cloud_billing.csv'
),
target AS (
    SELECT * FROM read_csv_auto('【权威CSV路径】') -- 例：'data/resource_inventory.csv'
)
SELECT COUNT(*) AS total_rows,
       COUNT(*) FILTER (WHERE target.【主键】 IS NOT NULL) AS matched_rows
FROM source
LEFT JOIN target ON source.【外键】 = target.【主键】;
```

### 空值结果怎样展示

- 字段少、终端能完整显示：保留上面的横向条件计数。
- 字段多、终端出现 `…`：改成纵向的“字段名 + 缺失行数”，避免隐藏结果被误判。

```sql
SELECT '【字段1】' AS field_name,
       COUNT(*) FILTER (WHERE 【字段1】 IS NULL) AS missing_rows
FROM read_csv_auto('【CSV路径】')

UNION ALL

SELECT '【字段2】',
       COUNT(*) FILTER (WHERE 【字段2】 IS NULL)
FROM read_csv_auto('【CSV路径】');
```

只替换 `【字段1】`、`【字段2】` 和 `【CSV路径】`；检查更多字段时，继续追加同结构的 `UNION ALL SELECT`。横向与纵向写法计算逻辑相同，只是展示方式不同。

### 把审计问题翻译成SQL

先翻译职责，再填写字段名：

```text
我要看什么结果 → SELECT
数据从哪里来 → FROM
哪些记录违反规则 → WHERE
按照什么类别汇总 → GROUP BY
汇总后保留哪些组 → HAVING
怎样排列结果 → ORDER BY
```

高频审计问题：

```text
数值范围审计
检查谁 → WHERE 【数值字段】 <= 【下限】
出错后用什么定位 → SELECT 【候选主键】
还要看到什么异常值 → SELECT 【数值字段】

枚举合法性审计
检查谁 → 【分类字段】
允许哪些值 → IN ('【合法值1】', '【合法值2】')
寻找非法值 → WHERE 【分类字段】 NOT IN (...)
出错后用什么定位 → SELECT 【候选主键】

枚举发现
查看实际出现哪些值 → SELECT DISTINCT 【分类字段】

空值审计
检查谁 → WHERE 【字段】 IS NULL
统计缺失数量 → COUNT(*) FILTER (WHERE 【字段】 IS NULL)
```

本项目示例：检查 `gpu_count` 是否大于0时，规则是 `gpu_count > 0`，审计查询应反向寻找违规记录，因此使用 `WHERE gpu_count <= 0`；`resource_pool_id` 只用于定位异常资源池，不是本轮被检查的字段。

本项目依次运行 `sql/02_data_audit.sql` 至 `sql/05_data_audit_resolution.sql`，职责见 [SQL导航](../sql/README.md)。

## 问题记录模板

```text
问题：【】
异常数量和比例：【】
证据样例：【】
分类：【真实错误 / 结构性空值 / 可接受噪声 / 待确认】
影响：【指标 / 连接 / 范围】
建议：【保留 / 标准化 / 回填 / 去重 / 排除 / 待确认】
依据：【数据字典 / 业务规则 / 权威表 / 时间顺序】
```

## 避坑

- 空值不等于0；不适用产生的空值不一定是错误；
- “ID不同”不代表不是重复；
- ID标准化提高关联率，但不能修复真正的业务错配；
- 低利用率可能承担容灾、P0服务或数据驻留责任；
- 只报异常数量而不说明影响和处理，审计没有完成。

## 完成标准

- 已检查结构、空值、重复、范围、枚举、关联和时间；
- 每个问题都有数量、分类、影响、依据和处理建议；
- 输出：`reports/data_audit.md`。

# 4｜数据清洗

## 思路

清洗是把已经确认的业务规则实现成可重复程序，不是凭感觉“让数据变漂亮”。

## 清洗决策卡

```text
审计问题：【】
业务证据：【】
处理动作：【保留 / 标准化 / 去重 / 回填 / 排除】
保留哪条记录及原因：【】
是否保留原始字段：【通常是】
允许变化的结果：【行数 / 空值 / 关联率】
绝对不能变化的结果：【金额 / 时间范围 / 其他】
验证方法：【】
```

## Pandas骨架

```python
df["【标准化ID】"] = (
    df["【原始ID】"].astype("string").str.strip().str.upper()
      .str.replace("_", "-", regex=False)
)

df["【数值字段】"] = pd.to_numeric(df["【数值字段】"], errors="coerce")
df["【UTC时间字段】"] = pd.to_datetime(df["【UTC时间字段】"], errors="coerce", utc=True)

df = (
    df.sort_values(["【业务键】", "【修订或时间字段】"])
      .drop_duplicates(subset=["【业务键】"], keep="last")
)
```

```powershell

```

## 映射检查

```text
原始字段 → 清洗字段：【】
缺失字段 → 权威来源：【】
重复业务键 → 保留优先级：【】
清洗表 → 下游指标：【】
```

## 避坑

- 不覆盖 `data/` 中的原始CSV；
- 不把所有缺失值填0；
- 不按任意行顺序去重；
- 回填时保留来源字段；
- 清洗后重新检查唯一性、关联率和金额。

## 完成标准

- 清洗规则可重复运行且有测试；
- 删除行数能由规则解释；

# 5｜探索分析

## 思路

先建立全貌，再逐层下钻。这个阶段回答“发生了什么”，不急着宣布原因。

```text
总量 → 趋势 → 结构 → 效率 → 业务切片 → 待验证异常
```

## 指标工作卡

```text
业务问题：【】
指标及完整公式：【】
主时间口径和粒度：【】
分析维度：【团队 / 产品 / 区域 / GPU / 采购方式 / 负载】
比较基准：【上期 / 目标 / 预算】
不可混合的单位：【】
预期支持的行动：【】
```

## SQL骨架

```sql
WITH grouped AS (
    SELECT 【维度】, SUM(【指标字段】) AS metric_value
    FROM 【清洗表】 WHERE 【统一口径】 GROUP BY 【维度】
)
SELECT 【维度】, metric_value,
       100.0 * metric_value / NULLIF(SUM(metric_value) OVER (), 0) AS share_pct
FROM grouped;
```

```sql
WITH monthly AS (
    SELECT DATE_TRUNC('month', 【时间字段】) AS metric_month,
           SUM(【指标字段】) AS metric_value
    FROM 【清洗表】 GROUP BY 1
)
SELECT *,
       100.0 * (metric_value / NULLIF(LAG(metric_value) OVER (ORDER BY metric_month), 0) - 1)
           AS month_over_month_pct
FROM monthly;
```

运行：`python run_sql.py sql/06_business_overview.sql`

## 结果说明模板

```text
事实：【指标】在【范围】为【数字】，相对【基准】变化【数字】。
变化集中在：【团队 / 产品 / 月份 / 采购方式】。
目前只能说明：【描述性事实】。
还不能判断：【原因或行动】。
下一步验证：【业务量 / 价格 / 效率 / 结构 / 事件】。
```

## 避坑

- 不对百分比进行无权重平均；
- 不从公司总量直接跳到单个异常资源；
- 不混合发票月和使用月；
- 不混合不同业务量单位；
- 不把同期变化直接写成因果。

## 完成标准

- 总量、趋势、结构和效率使用同一口径；
- 分项能够汇总回总计；
- 事实与待验证原因分开。

# 6｜成本归因

## 思路

先锁定总账，再直接归属，最后分摊共享费用。归因后总额必须回到原始总账。

## 归因设计卡

```text
总账来源：【】
计入费用类型：【】
单独展示或排除类型：【】
直接归属键：【】
字段优先级：【账单标签 / 资源清单 / 其他】
共享费用和分摊驱动：【】
最终归因粒度：【月 + 团队 + 产品 + 其他】
对账容差：【】
```

## 完整公式

```text
对象分摊权重 = 对象驱动量 ÷ 全部对象驱动量
对象共享费用 = 共享费用 × 对象分摊权重
对象总成本 = 直接成本 + 共享费用 + 调整与抵扣
对账差异 = 原始总账 - 所有对象归因后成本
```

## SQL骨架

```sql
WITH driver AS (
    SELECT 【对象】, SUM(【驱动字段】) AS driver_value
    FROM 【驱动表】 GROUP BY 【对象】
)
SELECT 【对象】,
       【共享费用】 * driver_value / NULLIF(SUM(driver_value) OVER (), 0) AS allocated_cost
FROM driver;
```

## 避坑

- `UnusedCommitment` 不与 `Commitment` 重复进入本项目总账；
- `Support` 没有资源池时不能被内连接丢掉；
- `PRD-SHARED` 不是最终产品归属；
- 分摊驱动要代表消耗或责任；
- 每增加一个维度都重新对账。

## 完成标准

- 所有费用被归属、分摊或明确标记未归属；
- 分摊权重合计为100%；
- 对账差异为0或在已说明容差内。

# 7｜原因分析

## 思路

先描述变化，再提出候选原因，再逐个找证据和反证。

```text
成本 = 业务量 × 单位业务GPU消耗 × GPU有效费率
再考虑采购结构、GPU型号、区域、产品结构和一次性事件
```

## 假设卡

```text
待解释现象：【指标 + 数字 + 时间 + 范围】
候选原因：【业务量 / 价格 / 效率 / 结构 / 事件】
如果成立应该看到：【可观察证据】
需要的数据和粒度：【】
对照对象或基准：【】
反证：【什么结果会推翻假设】
结论：【支持 / 部分支持 / 不支持 / 数据不足】
```

## 证据链模板

```text
事实：【】
范围匹配：【时间 + 团队/产品/区域】
机制：【为什么可能影响指标】
对照或反证：【】
结论强度：【事实 / 推断 / 假设】
剩余不确定性：【】
```

## 避坑

- 成本上涨但业务量没涨，不代表一定浪费；
- 事件的“预期影响”不是分析结论；
- 季节性、趋势和一次性调整要分开；
- 只挑支持假设的样例会产生确认偏误。

## 完成标准

- 每个主要变化至少检查业务量、价格、效率和结构；
- 原因结论有证据、机制、对照和限制；
- 事实、推断和假设明确区分。

# 8｜预测

## 思路

先建立简单基线，再做情景。预测展示假设变化如何影响成本和容量，不是假装知道唯一未来。

## 预测设计卡

```text
预测对象：【成本 / requests / jobs / k_pages / GPU容量】
历史和预测粒度：【】
预测范围与跨度：【】
基线方法：【上期值 / 移动平均 / 趋势】
验证窗口与误差指标：【】
情景：【基准 / 高增长 / 优化】
业务约束：【SLA / 合同 / 供应 / 兼容性】
```

## 基本公式

```text
MAE = Σ|实际值 - 预测值| ÷ 预测期数
MAPE = Σ(|实际值 - 预测值| ÷ |实际值|) ÷ 可计算期数 × 100%
单位业务容量消耗 = 活跃GPU小时 ÷ 同单位业务量
未来工作容量 = 未来业务量 × 单位业务容量消耗
未来总容量 = 未来工作容量 ÷ (1 - 最低备用容量率)
```

## 最小Python骨架

```python
monthly = df.set_index("【月份】")["【指标】"].sort_index()
forecast = monthly.rolling(3).mean().shift(1)
mae = (monthly - forecast).abs().dropna().mean()
```

## 避坑

- 不用同一批训练数据证明模型准确；
- 只有12个月数据时不使用无法验证的复杂模型；
- 不把不同业务量单位放进同一序列；
- 成本预测与容量预测不能互相替代；
- 情景假设必须可见。

## 完成标准

- 有简单基线、留出验证和误差；
- 至少有基准、高增长和优化情景；
- 容量预测包含备用要求和业务限制。

# 9｜优化

## 思路

优化不是把低利用率资源全部回收。每个行动都要同时计算收益、时间、约束和风险。

## 机会卡

```text
问题对象：【团队 / 产品 / 资源池 / 合同 / 流程】
证据：【成本 + 使用 + SLA + 事件】
建议行动：【具体动词】
当前基线与优化后假设：【】
年度毛节省：【】
一次性实施成本和新增运行成本：【】
首年净收益和回收期：【】
实施时间、负责人和完成标准：【】
SLA、容量、合同和技术风险：【】
试点与监控指标：【】
```

## 完整公式

```text
年度毛节省 = 当前基线年度成本 - 优化后年度成本
首年净收益 = 年度毛节省 - 一次性实施成本 - 首年新增运行成本
月度净节省 = 月度毛节省 - 月度新增运行成本
回收期（月） = 一次性实施成本 ÷ 月度净节省
```

## 优先级

```text
高：证据强、净收益高、风险低、可逆
中：收益明确，但依赖合同到期、迁移或跨团队协调
低：证据不足、风险高或需要先补数据
禁止直接执行：违反SLA、数据驻留、合同或容量安全
```

## 避坑

- `DR`、`WarmStandby` 或P0低利用资源不能直接回收；
- Reserved和Savings Plan到期前不能无成本取消；
- 不同GPU型号不能按张数等价替换；
- 理论节省不等于可实现净收益；
- 没有负责人、时间和监控指标的建议不是行动方案。

## 完成标准

- 每项建议可追溯到分析证据；
- 同时说明净收益、时间、SLA、容量和合同风险；
- 形成3—5项有优先级的行动。
