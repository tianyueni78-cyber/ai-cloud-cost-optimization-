# 05｜数据审计第三轮：结合业务上下文

## 目的

把空值和重复记录放回业务类型中解释，避免使用“只要为空就是脏数据”的错误规则。

## 输入

```powershell
git pull
python run_sql.py sql/04_data_audit_context.sql
```

## 关键输出与解释

### 使用指标的结构性空值

| 负载 | 总行数 | P95 延迟空值 | 排队时间空值 | 结论 |
|---|---:|---:|---:|---|
| Batch | 149,002 | 149,002 | 0 | 批处理不使用在线延迟指标 |
| Inference | 235,193 | 0 | 235,193 | 在线推理不使用训练排队指标 |
| Training | 122,704 | 122,704 | 0 | 训练不使用在线延迟指标 |

这些空值与字段定义完全一致，属于“不适用”，不是数据丢失。不能填成 0，因为 0 会被误解为实际测得零延迟或零排队。

### 账单空值

- 资源池空值共 86 条：84 条 `Support`、2 条 `Credit`，符合共享费用或供应商抵扣不绑定单一资源池的规则。
- GPU 小时和单价空值共 129 条：43 条 `Adjustment`、2 条 `Credit`、84 条 `Support`，均为非用量费用。
- 团队空值共 42 条：27 条 `Usage`、15 条 `UnusedCommitment`，需要继续判断能否通过资源池归属团队。
- 合同空值共 420 条，其中 312 条为 `Usage`，需要按采购方式继续解释。

### 业务约束

以下违规数量全部为 0：

- 活跃 GPU 超过分配 GPU；
- 业务量为负；
- 使用百分比超出 0–100；
- 资源池 GPU 数或有效费率不为正；
- 有效费率高于目录价；
- Credit 不为负、折扣为负或净额公式错误；
- SLA 日期、百分比或非负目标不合法。

“0 条违规”表示这些规则没有发现问题，不表示整张数据已经完全干净。

### 枚举值

负载类型、遥测状态、费用类型和采购方式的实际取值都属于数据字典允许值。数据字典中的允许值不要求本期全部出现，因此没有 `Commitment` 记录本身不能证明数据错误。

### 重复记录

- 相同 `usage_record_id` 的重复组：139。
- 内容完全一致：139 组。
- 内容冲突：0 组。

因此这 139 组可以在清洗层确定性去重，每组保留一行；原始 CSV 不修改。不同 ID 的 120 组业务重复仍需单独判断。

## 我学到的知识

- 空值分为“不适用的结构性空值”和“本应有值但丢失的异常空值”。
- 判断空值必须按业务类型分组，而不能只查看整列数量。
- 单列范围正常不代表跨字段关系正常，例如还要检查活跃量是否超过分配量。
- 完全重复可以确定性去重；业务键相同但记录 ID 不同不能直接删除。
- 原始层保留证据，清洗规则应写在新视图或新数据集中。
