# 06｜数据审计第四轮：确定处理规则

## 目的

解决第三轮剩下的三类问题：遥测指标空值、账单团队与合同空值，以及不同记录 ID 的业务重复。

## 输入

```powershell
git pull
python run_sql.py sql/05_data_audit_resolution.sql
```

## 输出与结果说明

### 1. 遥测空值与状态

| 状态 | 总行数 | GPU 利用率空值 | 显存利用率空值 | 可用性空值 |
|---|---:|---:|---:|---:|
| complete | 505,632 | 0 | 0 | 0 |
| late | 239 | 0 | 0 | 239 |
| partial | 1,028 | 630 | 398 | 0 |

结论：空值不是随机散落。利用率空值全部来自 `partial`，可用性空值全部来自 `late`。这些状态本身就是数据质量证据，应保留，不应把空值填成 0。

### 2. 账单团队归属

42 条团队缺失账单均有资源池，且全部能够通过标准化资源池 ID 关联资源清单并推导团队。

处理规则：新增归属团队字段，优先采用账单团队；账单团队为空时采用资源清单团队。不能直接覆盖原始字段，否则会丢失“供应商标签曾经缺失”的事实。

### 3. 合同空值

| 采购方式 | 总行数 | 合同空值 | 合同非空 |
|---|---:|---:|---:|
| OnDemand | 288 | 288 | 0 |
| Owned | 132 | 132 | 0 |
| Reserved | 473 | 0 | 473 |
| SavingsPlan | 316 | 0 | 316 |

承诺采购缺合同和非合同采购误带合同均为 0。420 条合同空值都符合采购方式，属于结构性空值。

### 4. 不同 ID 的业务重复

SQL 输出显示：

- 不同 ID 的重复组：120；
- 内容完全相同：0；
- 内容冲突：120；
- 混合遥测状态：0；
- 120 组全部为 `complete`。

进一步逐组核对发现，每组恰好有一条原始 ID 和一条 `-R` 修订 ID，且只有 `gpu_utilization_pct` 不同，其他关键指标相同。因此不能任意保留第一条，也不应取两条平均值；应保留带 `-R` 的修订记录。

## 最终清洗决策

| 情况 | 处理 |
|---|---|
| 相同 ID、内容完全重复 | 每组保留一行 |
| 原始 ID 与 `-R` 修订 ID 同时存在 | 保留 `-R` |
| ID 格式不一致 | 新增标准化 ID，保留原始 ID |
| 不适用字段为空 | 保持为空 |
| partial/late 遥测指标为空 | 保持为空，分析时报告覆盖率 |
| 账单团队为空但资源池可识别 | 新增推导团队和归属来源 |
| OnDemand/Owned 合同为空 | 保持为空 |
| 时间按月汇总 | 固定 UTC |

## 我学到的知识

- 数据质量状态可以解释空值来源，不能在清洗时丢掉。
- 回填字段时应同时保存来源，保证处理过程可追溯。
- 冲突记录的保留规则必须来自业务证据；看到两行不同不能随便选第一行。
- 数据审计的终点不是“没有任何空值”，而是每类异常都有明确、可解释、可执行的处理规则。
